    Lab 2 — Audit: how NotesApp stores passwords¶

    Your job: audit how NotesApp stores passwords. Prove the current storage is weak by breaking it, fix it, and measure how much the fix actually buys — in real numbers you record yourself. About 35–40 minutes, with your pair.

    What you hand in — a findings sheet, not code

    The deliverable is the Audit summary at the bottom: two findings and one measurement table, all short fills. Use AI for the code if you want — everyone will. AI cannot run your clock, read your capture, or make your severity call. That judgment is the graded part, and it is the part that is actually yours.

    Ethics — only your own data

    Every attack here runs only on a dump you generate yourself, from the course's own seed data, or on your own NotesApp clone. Same technique as a real leaked database — which is exactly why it only ever touches targets you are allowed to touch.

    Finding 1 — How fast can an attacker read the stored passwords?¶

    NotesApp today stores passwords in plain text — already the worst case. So instead, let's test the defense that feels safe and that many real apps shipped: "we hashed them" — with MD5, no salt. You are going to measure how strong that actually is.

    Predict first, with your pair

    You are handed a leaked table of 6 accounts, hashed with unsalted MD5. You attack it with a real public wordlist — the kind that actually circulates, not something we tailored to these accounts. Before you run it: how many of the 6 fall, and how long does it take? Will all of them? Write your guess down.

    How to build and run the attack (scaffolding — use it, or ask AI to)

    This is the mechanical part. Copy it, or have AI generate it — the point is the result, not the typing. The wordlist is a real one, not written around these passwords: some accounts will fall, some will not. That is the honest version of this attack.

    Make the folder and get the wordlist:

    mkdir -p crack

    ⬇ Download the wordlist (≈190 of the world's most common passwords, a small slice of what attackers really use) and save it as crack/wordlist.txt: common-passwords.txt

    crack/make_dump.py — a leaked table from "some other app", with a realistic spread of password strength. We hash each with unsalted MD5, exactly as that app would have:

    import hashlib

accounts = {
    "liwei": "123456",
    "sofia": "iloveyou",
    "tomk":  "qwerty123",
    "aisha": "password1",
    "marie": "mariepw",        # not a dictionary word - a predictable pattern
    "raj":   "Gv7#pLm2!xQ",    # long and random
}
with open("crack/leaked_users.txt", "w") as f:
    for username, password in accounts.items():
        # store "username:md5(password)" - unsalted MD5, exactly like the bad app would
        f.write(f"{username}:{hashlib.md5(password.encode()).hexdigest()}\n")
print("wrote crack/leaked_users.txt")

    crack/crack.py — tries every word in the real wordlist, and times itself:

    import hashlib, time

def load_dump(path):
    # read the leaked file into {username: md5_digest}
    out = {}
    with open(path) as f:
        for line in f:
            u, d = line.strip().split(":")   # each line is "username:digest"
            out[u] = d
    return out

accounts = load_dump("crack/leaked_users.txt")
wordlist = [w.strip() for w in open("crack/wordlist.txt") if w.strip()]

start = time.time()
cracked = {}
for candidate in wordlist:                       # for each guess in the wordlist...
    cd = hashlib.md5(candidate.encode()).hexdigest()   # hash the guess the SAME way the app did
    for u, d in accounts.items():                # ...compare it to every leaked digest
        if u not in cracked and d == cd:         # same digest => that guess IS the password
            cracked[u] = candidate
elapsed = time.time() - start

# the attack never "reverses" a hash - it just hashes guesses until one matches.
print(f"cracked {len(cracked)} / {len(accounts)} in {elapsed*1000:.1f} ms")
for u, p in cracked.items():
    print(f"  {u} : {p}")

    The key idea in the comments: cracking never reverses a hash. It hashes ordinary guesses and looks for a match — which is why a fast hash (MD5) and weak passwords are what make it work.

    Run it: python3 crack/make_dump.py && python3 crack/crack.py (Windows: use python instead of python3.)

    📏 Measure — record what you got

    Run the attack and read the output:

    • Accounts cracked: ___ / 6
    • Time taken: ___ ms

    Now compare with the guess you wrote down. Surprised?

    Finished running? Open this to debrief your result — not before

    Did every account fall? Look at your output. If any held out, work out what those passwords have in common before you open the answer. You know all 6 — they are in make_dump.py.

    The answer

    Two accounts survived. marie used mariepw — not a dictionary word, so it is not in the public list (yet — see the bonus). raj used a long random password that no wordlist contains. Cracking is not magic. It feeds on weak and predictable passwords. A fast, unsalted hash just makes each guess instant — it does not invent passwords the attacker never guesses.

    Remediation — migrate NotesApp to Argon2¶

    The stubborn objection — argue it with your pair before reading on

    Someone says: "raj's password survived even MD5. So the real fix is just — tell users to pick strong passwords. Why bother adding Argon2 at all?"

    Are they right? Take a minute and decide together.

    Here's the honest answer

    Half right — and getting the other half exact is the whole point of today.

    • True: a long random password like raj's is hard to crack even with MD5. For that one account, the user protected themselves. You are not wrong that strong passwords help.
    • But you are the developer, not the user. Your table holds everyone, and most people pick 123456. The question "is this password store safe?" is answered by the weakest password in it, not the strongest — one admin with password1 is already a breach.
    • You can advise strong passwords. You cannot enforce them. Argon2 is the one control that protects the users who didn't listen — and it costs you, the developer, almost nothing.

    So: a strong password protects you; Argon2 protects your users. A real system needs both, but only one of them is your job to guarantee — and it is the one you are about to build.

    Now fix it on the real app. You are adding Argon2 and upgrading each account the moment its owner next logs in — no migration script, no downtime. NotesApp should be running (docker compose up -d).

    How to apply the fix (scaffolding — three small changes)

    Add the dependency — edit web/requirements.txt, add argon2-cffi==23.1.0 (the Argon2 library), then docker compose build web (rebuilds the web image so the new library is installed inside it — editing the file alone does nothing until you rebuild).

    In web/app.py, near the imports:

    from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError, InvalidHash

    Just below app = Flask(__name__):

    ph = PasswordHasher()   # one reusable hasher: ph.hash(pw) to store, ph.verify(hash, pw) to check

def is_argon2_hash(value: str) -> bool:
    # every Argon2 hash starts with "$argon2"; a legacy plain-text password never does.
    # this is how login() tells a migrated account from a not-yet-migrated one.
    return value.startswith("$argon2")

    In the login() view, three changes:

    1. In the query, add , password to the SELECT and drop AND password = '...' from the WHERE (leave username concatenated — the SQL-injection flaw stays, it is December's class).

    2. Insert this block just before conn.close():

      authenticated = False
if row:
    stored = row["password"]
    if is_argon2_hash(stored):
        try:
            ph.verify(stored, password)
            authenticated = True
        except (VerifyMismatchError, InvalidHash):
            authenticated = False
    else:
        if stored == password:
            authenticated = True
            new_hash = ph.hash(password)
            conn.cursor().execute(
                "UPDATE users SET password = %s WHERE id = %s",
                (new_hash, row["id"]),
            )
            log(f"upgraded {row['username']} to argon2")

    3. Change the if row: line (after conn.close()) to if authenticated:. Everything below it stays as-is.

    Apply it: docker compose up -d --build (--build rebuilds the image with your new app.py, -d runs it in the background).

    Whatever writes the code — you must understand the else branch

    That else branch is the whole idea: an old plain-text account is checked once, then silently re-hashed with Argon2 on that login. If AI wrote it for you, read it until you can explain it — the next prediction depends on you getting this.

    Predict — before you look at the database

    Log in once as alice / alicepw (normal login, nothing special). Then, before you query the DB: what does alice's stored password hold now — still alicepw, or something else? Why?

    Check it, and were you right? 
    # peek straight into the database, bypassing the app:
#   exec db       -> run a command in the 'db' container
#   psql -U ... -d -> open the Postgres client as user 'notesapp' on db 'notesapp'
#   -c "SELECT..." -> run one query and exit: show how alice's password is stored
docker compose exec db psql -U notesapp -d notesapp -c "SELECT username, password FROM users WHERE username = 'alice';"

    It now shows $argon2id$v=19$m=65536,t=3,p=4$... — a long Argon2 hash, not alicepw. Her one normal login hit the else branch, which re-hashed and wrote it back. No reset, no downtime — this is how real systems migrate password storage on live users.

    Checkpoint — the app is now in the right state

    alice is migrated. Log out and back in once more — it still works, now via the is_argon2_hash branch. The app ends this lab with Argon2 storage. Leave it running for the next measurement.

    Finding 2 — How much did the fix actually buy? (measure)¶

    Same attacker, same laptop. The only thing that changed is the hash algorithm's speed. Measure the difference yourself.

    Predict first

    MD5 just cracked 6 accounts in milliseconds. Argon2 is built to be slow on purpose. Guess the ratio: Argon2 is how many times slower per guess than MD5? 10×? 1000×? More?

    How to measure (one command — runs inside the web container, which has Argon2) 
    # "docker compose exec web python -" runs a Python script (fed on stdin, between <<'PY' and PY)
# INSIDE the web container, which is the one place argon2 is installed.
docker compose exec web python - <<'PY'
import hashlib, time
from argon2 import PasswordHasher

N = 100_000
t = time.time()
for _ in range(N):                       # hash 100,000 times to get a stable rate
    hashlib.md5(b"guess").hexdigest()
md5_rate = N / (time.time() - t)         # guesses per second for MD5
print(f"MD5    : {md5_rate:,.0f} guesses/second")

ph = PasswordHasher()
t = time.time()
ph.hash("guess")                         # ONE Argon2 hash - already slow enough to measure alone
one = time.time() - t
print(f"Argon2 : {one*1000:.0f} ms for ONE guess  ({1/one:.1f} guesses/second)")
PY

    Why this isn't the same as re-running the crack

    You are measuring raw guessing speed, which is what actually decides whether a real attacker (with a wordlist of millions, not ~190) wins. The wordlist is the same for both hashes — only the per-guess cost changed, and that is the entire story of Argon2.

    Finished early? (optional) — crack marie with a guessing rule

    marie's password (mariepw) is not in any public wordlist, so the dictionary attack missed it. But it follows a pattern — <username>pw — and an attacker who spots a pattern can generate guesses from it. Add rule-based candidates and test them too:

    rule_based = [f"{u}pw" for u in accounts]
candidates = wordlist + rule_based

    (loop over candidates instead of wordlist). Now marie falls — 5 of 6. Only raj, the long random password, still survives. That is the jump from a plain dictionary attack to a rule-based one — Hashcat and John the Ripper are built around exactly this. Add a note to your audit: "the wordlist size is not the limit; attacker creativity is — the only thing that held was a password with no pattern at all."

    Troubleshooting¶

    ModuleNotFoundError: No module named 'argon2'

    You edited requirements.txt but did not rebuild. Run docker compose build web, then docker compose up -d.

    Login always fails after the fix

    Indentation — the if authenticated: block must sit exactly where the old if row: was. Check the container logs: docker compose logs web (an IndentationError confirms it).

    DB still shows the plain password after login

    Confirm you are hitting the rebuilt container: docker compose ps should show web with a recent CREATED time.
