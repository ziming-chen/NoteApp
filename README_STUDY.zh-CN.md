## 先理解这次作业在做什么

NotesApp 是一个成绩系统。学生看自己的成绩，老师录入成绩和评语，管理员管理账号。老师要求两项成果：一张有编号的数据流图（Data-flow diagram），一张与编号对应的 STRIDE 表格。

数据流就是“谁把什么信息发送给谁”。例如，你在登录页面填写账号和密码，浏览器把它们发给 Flask 服务器，这就是一条数据流。服务器再向数据库查找用户，也是另一条数据流。它们需要分别编号，因为危险点不同。

## 用一次登录串起整张图

以 `alice` 登录为例：

1. **01**：浏览器提交用户名和密码给 Flask。
2. **14**：Flask 向 PostgreSQL 发送用户查询。
3. **16**：数据库返回用户编号、用户名和角色。
4. **04**：Flask 返回登录会话信息，浏览器之后会带上 cookie。
5. **02**：浏览器请求自己的成绩页面。应用再次通过 **14、16** 查询成绩，并通过 **04** 返回 HTML。
6. 点击页面的 **Load** 后，**03** 请求一条成绩的 JSON 数据，**04** 返回结果。

这里的 cookie 与 JWT 是两种不同的身份传递方式。本项目的网页主要使用会话 cookie；学生页面的 JavaScript 使用 JWT 调用成绩 API。知道用户名不等于有访问权限，服务器应当检查身份和记录归属。

老师的 **05–08** 对应登录、查看或导出成绩、提交成绩表单及接收结果。管理员的 **09–13** 对应登录、控制台、账号表单、服务器测试及返回结果。

**15** 是数据库写入。这次没有提交成绩或账号修改，所以它来自表单和源代码分析。**17、18** 是管理员正常 ping 的命令及返回内容。**19** 是应用向日志文件写记录。

## 两条信任边界怎么理解

**TB1：浏览器与应用之间。** 浏览器里的数据可以被用户改变，因此服务器不能因为页面上写着“学生”就相信用户一定是学生。账号、密码、cookie、JWT、成绩编号和表单输入都需要检查。

**TB2：应用与数据库之间。** 数据库根据连接账号和 SQL 执行操作。应用必须把输入安全地传入查询，并限制查询或修改范围。浏览器只显示自己的成绩，并不能证明数据库查询一定检查了归属。

服务器内部的 shell 与日志文件共享应用容器的操作系统身份。它们是重要资源，但不是图中一个新登录用户。Docker socket 和 `/host` 挂载让容器能接触更多资源，所以还需要查看部署权限。

## STRIDE：每条箭头都问六个问题

| 字母 | 英文 | 中文含义 | 放到成绩系统里怎么问 |
| --- | --- | --- | --- |
| S | Spoofing | 冒充身份 | 别人能否冒充 alice、老师或管理员？ |
| T | Tampering | 篡改 | 输入、成绩、评语、请求或结果能否被改动？ |
| R | Repudiation | 抵赖 | 做过操作后，是否缺少可靠记录，无法追查？ |
| I | Information disclosure | 信息泄露 | 不该看到的人能否看到成绩、评语、凭据或内部信息？ |
| D | Denial of service | 拒绝服务 | 大量请求或耗时操作能否使正常用户无法使用？ |
| E | Elevation of privilege | 权限提升 | 用户或程序能否获得超出原本身份范围的能力？ |

例如分析 **03 成绩 API**：

- **S**：盗取或伪造令牌可能冒充另一个用户。
- **T**：修改成绩编号会改变读取目标；这个读取接口本身不会修改成绩。
- **R**：接口没有记录每次读取，之后难以追查谁查看了哪条记录。
- **I**：源码查询没有成绩所有者条件，存在泄露他人成绩的风险。
- **D**：大量请求会占用应用和数据库资源。
- **E**：获得读取他人记录的权限，会越过原本的用户数据边界。

注意：这是“可能出现什么威胁”。这次只读取 alice 自己的记录，没有通过读取别人的记录来验证漏洞。英文表格中的每个威胁也不是一次成功攻击的证明。

## 从哪里看源代码

先读 [web/app.py](web/app.py)，不用从头理解全部 Python 语法。可以按下面的顺序定位函数：

| 函数 / 文件 | 看什么 | 为什么值得看 |
| --- | --- | --- |
| `login()` | 输入如何进入 SQL，登录后保存什么身份。 | 直接对应 01、05、09、14。 |
| `dashboard()` | 查询有没有限制为当前学生。 | 页面是否真正只取自己的成绩。 |
| `api_notes()` | 有没有检查成绩记录属于当前用户。 | 已登录不等于可以读取全部记录。 |
| `teacher()` / `export_csv()` | 是否限制到当前老师负责的课程。 | 角色检查之外还要检查对象范围。 |
| `grades()` | 修改成绩前检查了什么。 | 写入应检查老师与目标成绩的关系。 |
| `verify_jwt()` | 如何处理算法和签名。 | 令牌内容不能未经验证就信任。 |
| `admin_ping()` | 输入是否进入 shell 命令。 | 文本输入一旦被当成命令语法，影响会扩大。 |
| `log()` / `admin_users()` | 记录了哪些操作，哪些没有。 | 日志不足或可修改会导致难以追查。 |
| `web/templates/dashboard.html` | 评语是否转义。 | HTML 文本与可执行页面内容需要区分。 |
| `web/Dockerfile` / `docker-compose.yml` | 容器用户、文件权限、挂载、端口。 | 程序漏洞的影响也取决于运行权限。 |

**认证（Authentication）** 回答“你是谁”。**授权（Authorization）** 回答“你可以操作哪些东西”。知道对方是老师后，还要检查目标成绩是否属于这位老师负责的课程。

## 在自己的 Windows 上打开

项目正式位置：`D:\AAAdile\Work\Cybersecurity\NoteApp`。桌面的 **Work** 快捷方式可以打开 `D:\AAAdile\Work`。

1. 打开 **Docker Desktop**，等待引擎运行。
2. 在 NoteApp 文件夹双击 `Start-NoteApp.cmd`。
3. 浏览器打开 <http://localhost:8080>。
4. 用课程演示账号登录：学生 `alice / alicepw`，老师 `prof.turing / teach123`，管理员 `admin / admin123`。
5. 完成后双击 `Stop-NoteApp.cmd`；它保留数据库卷中的记录。

也可以在 PowerShell 中运行：

```powershell
Set-Location 'D:\AAAdile\Work\Cybersecurity\NoteApp'
docker compose -p noteapp -f docker-compose.yml -f compose.windows.yml up -d --build --wait
docker compose -p noteapp -f docker-compose.yml -f compose.windows.yml ps
```

`web` 是网站容器，`db` 是数据库容器。**Image（镜像）** 可以理解为程序和运行环境的模板；**Container（容器）** 是由镜像启动的运行实例；**Volume（卷）** 保存数据库数据，容器停止后数据仍可保留。

本项目通过 Windows 的 Docker Desktop 管理容器，不需要你进入 Ubuntu 终端。容器中的应用运行在 Linux 环境，这与“必须在 Ubuntu 中做作业”不是同一回事。

`compose.windows.yml` 只调整本机端口：网站使用 `127.0.0.1:8080`，数据库使用 `127.0.0.1:15432`。数据库容器内部仍使用 5432，网页容器内部使用 5000。

课程应用中保留了教学用安全问题。后续练习的操作范围和交付要求，要以对应课件为准。

## 第四节课新增：导出文件完整性校验

当前导出的 CSV 会在四列成绩数据之后附上一行 HMAC。教师页新增 **Verify an exported CSV**，可上传原件验证；改动成绩后校验会失败。校验不导入成绩，也不会修改数据库。启动器会保留并加载独立的 HMAC 密钥。

操作步骤、演示文件与原理见 [第四节课中文说明](docs/session04/README_STUDY.zh-CN.md)，另有 [英文报告](docs/session04/README.md)。本文件前面的 Session 02 记录是历史观察；旧导出没有 HMAC，不会自动变成可验证的文件。
